# عقد الربط السحابي لتطبيق Social Najhin

**الإصدار:** 1.0.0 — **الوجهة:** مطوّر الموقع الخارجي / GenSpark.

هذه مواصفات لخدمة مستقبلية، وليست خدمة منشورة أو تغييرًا مطبقًا في Electron.
لم نغيّر قاعدة بيانات Replit أو نظام الرخصة المحلي أو مفاتيح التوقيع.
العنوان `https://api.your-domain.invalid` مثال غير صالح للتشغيل؛ يستبدل بعد نشر الموقع.

## الملفات

- `openapi.yaml`: العقد الدقيق للطلبات والردود والأخطاء.
- `schema.sql`: مخطط PostgreSQL مرجعي للموقع الخارجي؛ لا تنفّذه على قاعدة التطبيق الحالية.
- هذا الملف: قواعد التنفيذ والأمان وتسلسل الربط واختبارات القبول.

## 1. فصل تسجيل الدخول عن حق استخدام التطبيق

نجاح تسجيل الدخول لا يعني وجود شراء أو اشتراك أو مكان متاح لجهاز جديد.
الموقع هو صاحب القرار، وElectron يعتمد `entitlement.app_access`، لا قيمة مخزنة يختارها المستخدم.

نموذج المنتج الحالي هو **شراء دائم مع اشتراك للتحديثات والدعم**.
لذلك انتهاء الدعم لا يوقف حق الاستخدام الدائم:

| access_model | شروط eligible قبل فحص الجهاز |
|---|---|
| perpetual | الحساب active، وسجل الاستحقاق موجود وحالته active؛ لا يشترط اشتراك دعم سارٍ |
| subscription | الشروط السابقة، واشتراك active أو trialing، وcurrent_period_end بعد وقت الخادم |
| none | لا يوجد استحقاق؛ eligible=false |

`app_access = eligible AND device.status == "active"`.
`updates_allowed = eligible AND support_until != null AND support_until > server_time`.
إذا لم يوجد استحقاق تكون حدود الأجهزة 0. لا تمنح التسجيلات الجديدة حق استخدام تلقائيًا.
`cancel_at_period_end=true` مع status=active يبقي الاشتراك صالحًا حتى نهاية الفترة؛
حالات past_due/canceled/expired لا تمنح استخدامًا يعتمد على الاشتراك في هذا العقد.
استخدام نموذج subscription لإيقاف التطبيق بانتهاء الاشتراك قرار تجاري صريح، وليس تحويلًا تلقائيًا للحسابات الدائمة.

**اختيار reason:** عند عدم الأهلية استخدم NO_ENTITLEMENT أو ENTITLEMENT_SUSPENDED
أو ENTITLEMENT_REVOKED أو SUBSCRIPTION_INACTIVE أولًا. عند الأهلية: DEVICE_BLOCKED
للجهاز المحظور، DEVICE_NOT_ACTIVE للجهاز غير النشط، وإلا OK.
`app_access=false` إذا كان أي شرط مطلوب غير متحقق، حتى لو كان reason الأول متعلقًا بشرط آخر.

## 2. تسلسل Electron المطلوب لاحقًا

1. يحصل main process على Machine ID الموجود في التطبيق؛ قيمة SHA-256 من 64 خانة hex صغيرة.
   لا يرسل معرف النظام الخام، ولا يقبل Device ID يختاره مستخدم من واجهة الإعدادات.
2. يستقبل البريد وكلمة المرور **أو** رمز الدخول الشخصي عبر IPC محدود ومتحقق من مرسل النافذة.
3. يستدعي `POST /v1/desktop/auth/login`. لا يرسل الطريقتين معًا.
4. يتخلص من كلمة المرور/رمز الدخول الأصلي بعد الطلب. لا يحفظهما ولا يسجلهما.
5. يحفظ refresh token باستخدام Electron `safeStorage` في ملف داخل userData بصلاحيات مقيدة.
   يحفظ access token في ذاكرة main process؛ لا يرسل أي رمز إلى renderer أو localStorage.
   إذا لم يتوفر تشفير آمن، لا يحفظ الجلسة؛ يتيح تسجيل دخول مؤقتًا في الذاكرة مع تنبيه واضح.
6. يعرض معلومات الحساب والاستحقاق. إذا كان eligible=true والجهاز غير نشط، يستدعي
   `POST /v1/desktop/devices/activate` بلا body، ثم يعتمد الرد الجديد.
7. إذا بلغ الحساب حد الأجهزة، يعرض DEVICE_LIMIT_REACHED ورابط إدارة الحساب في الموقع؛
   لا يحذف جهازًا آخر تلقائيًا ولا يخفي المشكلة بإظهار «تم التفعيل».
8. عند كل تشغيل/استئناف يفحص `GET /v1/desktop/entitlement`، ثم يعيد الفحص كل
   check_after_seconds بحد أقصى 900 ثانية. تبقى الإعدادات والخروج والمساعدة متاحة عند الرفض.
9. يبقى منع العمليات المحمية في **backend/main** أيضًا، لا في تعطيل الأزرار فقط.
   لا ينفذ عملية محمية بعد انتهاء صلاحية آخر قرار إيجابي دون فحص ناجح جديد.
10. عند 401 يجدد مرة واحدة بطلب refresh متسلسل؛ إذا فشل يمسح الجلسة ويطلب الدخول.
    لا تجدد حلقة بلا نهاية ولا تعاود refresh تلقائيًا بعد timeout غامض: قد يكون الخادم استهلك الرمز.
11. الخروج يلغي الجلسة، ولا يحرر مكان الجهاز. فك ربط الجهاز إجراء منفصل بتأكيد المستخدم،
    يلغي جميع جلساته ويحرر المكان في معاملة واحدة.

**حدود الاتصال:** access token مدته 900 ثانية، والجلسة تنتهي نهائيًا بعد 30 يومًا من الدخول.
يجدد العميل قبل انتهاء access token، لكن لا يمدّد عمر الجلسة النهائي.
في آخر 900 ثانية من عمر الجلسة يرفض refresh ويطلب دخولًا جديدًا بدل إصدار access token يتجاوز نهاية الجلسة.
`offline_grace_seconds=0`: لا توجد رخصة عمل دون اتصال في العقد السحابي الأول.
تعذر الاتصال يعرض «تعذر التحقق» وليس «اشتراك منتهي»؛ تنتهي صلاحية القرار السابق خلال 900 ثانية كحد أقصى.
استخدم مؤقتًا رتيبًا للفواصل وأعد التحقق عند الاستئناف؛ لا تعتمد على تغيير ساعة الجهاز.
قد تتأخر ملاحظة الحظر في التطبيق حتى موعد الفحص التالي؛ لا تدّع إلغاءً لحظيًا أثناء انقطاع الاتصال.

## 3. المسارات

| Method | Path | الوظيفة |
|---|---|---|
| POST | /v1/desktop/auth/login | دخول وإنشاء جلسة مرتبطة بالجهاز، دون حجز مكان |
| POST | /v1/desktop/auth/refresh | تدوير رمزي الوصول والتجديد |
| POST | /v1/desktop/auth/logout | إلغاء الجلسة الحالية فقط |
| POST | /v1/desktop/devices/activate | تفعيل جهاز الجلسة ضمن الحد |
| GET | /v1/desktop/entitlement | قرار الاستخدام والتحديثات والاشتراك |
| GET | /v1/desktop/devices | قائمة أجهزة الحساب، مع pagination |
| DELETE | /v1/desktop/devices/current | فك ربط الجهاز الحالي وإلغاء جميع جلساته |

كل المسارات عدا login وrefresh تتطلب `Authorization: Bearer <ACCESS_TOKEN>`.
ردود 204 بلا body؛ بقية الردود JSON. حد body المقترح 4 KiB.
كل الردود `Cache-Control: no-store`. حالات 429 تتضمن `Retry-After` بالثواني.

### مثال دخول بالبريد

```json
{
  "email": "customer@example.com",
  "password": "<USER_PASSWORD>",
  "device": {
    "device_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "name": "Customer Mac",
    "platform": "darwin",
    "app_version": "1.0.3"
  }
}
```

بديل البريد وكلمة المرور: المفتاح `auth_token` بقيمة `snp_` تليها 64 خانة base64url،
مع كائن device نفسه. هذا رمز شخصي يصدره الموقع بعد تسجيل دخول موثوق،
**ليس** كلمة مرور لوحة البائع، وليس مفتاح SN1، وليس مفتاح API إداريًا عامًا.
لا توجد علاقة بين معرف الجهاز العام ورمز المصادقة السري.

### مثال رد التحقق بعد تفعيل جهاز يملك شراءً دائمًا ودعمًا منتهيًا

```json
{
  "user": {
    "user_id": "11111111-1111-4111-8111-111111111111",
    "email": "customer@example.com",
    "status": "active"
  },
  "device": {
    "device_id": "aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
    "name": "Customer Mac",
    "platform": "darwin",
    "app_version": "1.0.3",
    "status": "active",
    "is_current": true,
    "activated_at": "2026-10-29T10:00:00Z",
    "last_seen_at": "2026-10-29T10:10:00Z"
  },
  "entitlement": {
    "eligible": true,
    "app_access": true,
    "access_model": "perpetual",
    "reason": "OK",
    "updates_allowed": false,
    "support_until": "2026-10-01T00:00:00Z"
  },
  "subscription": {
    "status": "expired",
    "current_period_end": "2026-10-01T00:00:00Z",
    "cancel_at_period_end": false
  },
  "device_limits": { "max_devices": 1, "active_devices": 1 },
  "server_time": "2026-10-29T10:10:00Z",
  "check_after_seconds": 900,
  "offline_grace_seconds": 0
}
```

### الأخطاء

```json
{
  "error": {
    "code": "DEVICE_LIMIT_REACHED",
    "message": "The account has reached its device limit.",
    "request_id": "22222222-2222-4222-8222-222222222222"
  }
}
```

يعتمد Electron على code الثابت لترجمة الرسالة AR/EN، لا على نص message.
401 للمصادقة غير الصالحة، 403 لمنع الحساب/الأهلية/الجهاز، 409 لحد الأجهزة،
429 للتقييد، 503 لتعذر الخدمة. بيانات دخول خاطئة تعطي رسالة عامة دون كشف وجود البريد.
رد entitlement بقيمة app_access=false قد يكون 200: هذا نجاح قراءة وليس نجاح تفعيل.

## 4. الجداول والحقول المهمة

| الجدول | الغرض والحقول الأساسية |
|---|---|
| app_users | user_id، email، password_hash، external_identity_id، status |
| app_entitlements | user_id، access_model، status، max_devices، support_until |
| app_subscriptions | user_id، status، current_period_start/end، cancel_at_period_end |
| app_devices | id داخلي، user_id، device_id، status، platform، activated_at، revoked_at |
| app_desktop_sessions | session_id، user_id، device_row_id، access_token_hash، expires_at، revoked_at |
| app_refresh_tokens | session_id، token_hash، used_at، replaced_by، expires_at |
| app_personal_login_tokens | user_id، token_hash، scope، expires_at، revoked_at |
| app_security_events | event_type، user_id، reason_code، request_id، created_at |

يحسب active_devices من الصفوف ذات status=active؛ ليس رقمًا يقبله الخادم من العميل.
يحدد max_devices من استحقاق الحساب: مثل 1 أو 5 أو 10 أو 50.
الاشتراك الحالي صف واحد لكل مستخدم؛ تاريخ الفواتير وأحداث مزود الدفع محفوظ في الموقع بصورة مستقلة.
لا يحتاج العقد إلى بيانات البطاقة أو مفاتيح مزود الدفع داخل Electron.

### منع تجاوز حد الأجهزة بالتزامن

قيد UNIQUE(user_id, device_id) وحده لا يمنع جهازين مختلفين من أخذ آخر مكان في الوقت نفسه.
يجب قفل صف الاستحقاق `SELECT ... FOR UPDATE` داخل transaction، ثم فحص الأهلية،
ثم قفل الجهاز وعد الأجهزة الفعالة، ثم تخصيص المكان. إعادة تفعيل الجهاز النشط idempotent.
تستخدم كل عمليات المقاعد، بما فيها لوحة الموقع وتعديل الحد، القفل نفسه والترتيب نفسه.
لا تخفض max_devices تحت عدد الأجهزة الفعالة دون إجراء إداري واضح.
لا يؤدي GET إلى حجز مكان أو إعادة جهاز مفصول. تحدّث last_seen_at أثناء المصادقة
كتتبّع فقط، دون تغيير حالة الجهاز أو الاستحقاق.

عند login لجهاز موجود، لا تجعل blocked أو revoked نشطًا تلقائيًا.
الجهاز revoked يمكنه تفعيل نفسه فقط من جلسة دخول جديدة بعد revoked_at.
الجهاز blocked يحتاج رفع الحظر من الموقع؛ لا يكفي الدخول مرة أخرى.

## 5. قواعد أمان الخادم

- HTTPS موثوق فقط. يمنع Electron إعادة التوجيه إلى مضيف آخر أو تعطيل فحص الشهادة.
  عنوان الخدمة يثبت في إعدادات بناء يملكها البائع، لا حقلًا يسمح للمستخدم بإرسال كلمة مروره إلى أي عنوان.
- لا تحفظ كلمات المرور نصيًا؛ استخدم Argon2id بإعدادات مكتبة موثوقة.
  يمكن ربط مستخدمي الموقع بنظام هوية موجود عبر external_identity_id بدل إنشاء نظام كلمات مرور آخر.
  طبّع البريد بإزالة المسافات المحيطة وتوحيد الحالة؛ لا تقص كلمة المرور أو تغيّر محتواها.
- ينشئ الخادم الرموز عشوائيًا تشفيريًا: access من 32 bytes، refresh من 48 bytes،
  والرمز الشخصي من 48 bytes مع بادئة snp_. تخزن SHA-256 للرموز عالية العشوائية فقط.
- كل وصول يفحص جلسة الخادم وصلاحيتها وعدم إلغائها وحالة الحساب والجهاز؛ ليست مصادقة JWT
  تقبل رمزًا ملغيًا إلى أن تنتهي مدته. الجهاز pending مسموح لجلسة الحساب، وليس لتشغيل ميزات التطبيق.
- refresh يقفل الصفوف ويستهلك القديم وينشئ البديل ويبدل access token في transaction واحدة.
  احتفظ ببصمات الرموز المستخدمة حتى نهاية الجلسة لاكتشاف الإعادة؛ عند replay ألغِ العائلة
  وثبّت الإلغاء في قاعدة البيانات قبل رد الخطأ، لا تتراجع عنه ضمن rollback.
- الرمز الشخصي يظهر مرة واحدة في الموقع. إلغاؤه يلغي الجلسات المرتبطة به عبر login_token_id.
  يحتاج إصداره/إلغاؤه تسجيل دخول حديثًا في الموقع، وليس desktop bearer token.
- تعليق الحساب يلغي جميع الجلسات فورًا. سحب الاستحقاق يمنع القرار الإيجابي، حتى لو بقيت جلسة قراءة الحساب.
- طبّق rate limits للدخول والتجديد والتفعيل حسب IP ومعرف حساب محمي. حد الجلسات المقترح
  10 لكل جهاز و20 جهازًا pending لكل حساب لمنع تراكم السجلات؛ لا تربطهما بحد المقاعد المدفوعة.
- لا تثق في user_id/status/max_devices/app_access أو السعر إذا أرسلها العميل.
  ارفض الحقول الزائدة والـJSON غير المطابق للعقد، واستخدم prepared statements.
- لا تسجل Password أو Authorization أو الرموز أو body تسجيل الدخول. نظف أدوات تتبع الأخطاء أيضًا.
- تحتاج ردود الجهاز وقوائم الحساب إلى owner filtering من هوية الجلسة، لا شرط مصدره query.
- استخدم دور قاعدة بيانات محدود الصلاحيات للخدمة ونسخًا احتياطيًا وسياسة حذف واحتفاظ مناسبة.
  لا تمنح الواجهة الأمامية كتابة مباشرة في جداول الاستحقاقات أو الجلسات أو الرموز.
  عند استخدام Supabase/PostgREST طبّق RLS وسياسات الملكية المناسبة أو امنع الوصول المباشر،
  واجعل التغييرات الحساسة من خادم موثوق فقط؛ لا ترسل service-role key إلى المتصفح.
- بصمة الجهاز ليست إثبات hardware attestation ولا تمنع نسخ عميل معدل. التطبيق المصدر يمكن تعديله؛
  الإنفاذ القوي للموارد السحابية يجب أن يكون على الخادم أيضًا.
- تحديث الدفع يتم عبر webhook متحقق التوقيع وبمعالجة idempotent على الموقع. نجاح صفحة redirect
  أو ادعاء العميل بالدفع لا يمنح استحقاقًا. تفاصيل مزود الدفع خارج نطاق هذا العقد.

## 6. الانتقال من الرخصة المحلية

يبقى بناء Electron الحالي يعمل بالرخصة المحلية حتى تجهيز الخدمة واختبارها.
عند التنفيذ اللاحق يضاف وضع مستقل باسم cloud وعنوان API مثبت، ولا يعاد استخدام
mode=online القديم: فهو خاص بتبادل مفاتيح SNK وشهادات SN1، وليس جلسات حسابات الموقع.
في وضع cloud لا يوجد fallback تلقائي للرخصة المحلية عند فشل الموقع؛ فهذا يتجاوز قرار المنع.
لا تحذف شهادات المستخدم المحلية أثناء تجربة الربط أو تبدل معرفات الأجهزة.
تحتاج الحسابات التي تملك تراخيص حالية إلى ربط موثوق من البائع؛ لا يكفي لصق أي مفتاح محلي لمنح شراء سحابي.

الإصدارات القديمة وشهاداتها الدائمة لا يمكن إلغاؤها عن بُعد.
لا تعد بأن فك ربط مقعد سحابي يوقف نسخة offline قديمة أو يضمن حدًا موحدًا بين النظامين.
سياسة انتقال العملاء وإعادة تخصيص المقاعد تحتاج قرارًا منفصلًا قبل الإطلاق.

## 7. نص جاهز لتسليمه إلى GenSpark

> ابنِ موقع الحسابات والاشتراكات لـ Social Najhin. استخدم الملفات الثلاثة المرفقة
> كمصدر مواصفات ملزم، ونفّذ OpenAPI كما هو، مع PostgreSQL من schema.sql.
> المطلوب backend حقيقي وقاعدة بيانات مستمرة، وليس mock أو بيانات ثابتة.
> أنشئ واجهة حساب تعرض حق الاستخدام، الدعم، الأجهزة والحد، وتسمح بإصدار رمز desktop:login
> مرة واحدة بعد إعادة مصادقة، وإلغائه وإلغاء جلساته المرتبطة. افصل صلاحيات المشتري عن الإدارة.
> لا تنشئ استحقاقًا عند التسجيل؛ ينشئه شراء موثوق أو مسؤول.
> نموذج access_model الافتراضي perpetual يحافظ على شراء التطبيق الدائم؛ الاشتراك للتحديثات
> والدعم لا يوقف الاستخدام الدائم. لا تختَر مزود دفع أو تغيّر التسعير دون تحديدهما لاحقًا.
> نفّذ معاملات المقاعد وتدوير الرموز وكشف replay وحدود الطلبات والـowner filtering.
> وفر صفحة سياسة الخصوصية وآليات استرجاع الحساب من مزود الهوية الموثوق.
> أعد عنوان HTTPS الفعلي، نسخة OpenAPI المنشورة، وأمثلة ردود من بيئة اختبار،
> وحساب اختبار يُقدّم بطريقة آمنة، وتقرير نتائج اختبارات القبول أدناه.
> لا تضع مفاتيح إدارية أو كلمات مرور أو private signing keys في كود الواجهة.

## 8. اختبارات قبول مطلوبة من مطوّر الموقع

1. دخول صحيح بالطريقتين؛ دخول خاطئ عام؛ رفض الطريقتين معًا والحقول غير المتوقعة.
2. حساب بلا شراء يستطيع قراءة حالته لكن لا يحجز مقعدًا ولا يحصل على app_access=true.
3. تفعيل جهاز وإعادة الطلب لا يضاعف العدد؛ جهازان يتنافسان على آخر مقعد لا ينجحان معًا.
4. حد الأجهزة يعطي 409 ولا يحذف أي جهاز. لا يستطيع حساب قراءة أجهزة حساب آخر.
5. شراء perpetual مع دعم منتهٍ يبقى app_access=true وupdates_allowed=false.
6. نموذج subscription مع فترة منتهية أو past_due يمنع الاستخدام، دون تفسير العطل الشبكي كاشتراك منتهٍ.
7. GET لا يفعّل pending/revoked. blocked لا يستطيع تجاوز الحظر بتسجيل دخول جديد.
8. تدوير refresh يلغي access القديم؛ إعادة استخدام refresh مستهلك تلغي العائلة كلها.
9. logout لا يحرر المقعد؛ DELETE current يحرره ويلغي كل جلسات ذلك الجهاز.
10. تعليق الحساب/إلغاء الرمز الشخصي/بلوغ نهاية الجلسة يمنع كل الرموز المتأثرة.
11. إعادة محاولات rate-limited تحترم Retry-After، وكل الردود no-store دون تسريب أسرار في السجلات.
12. قبل ربط Electron: اختبر الانقطاع، الاستئناف، انتهاء الرموز، وفشل تشفير النظام دون منح وصول صامت.
